# Infrastructure project style

The generated CDK app is emitted in one of two shapes, recorded as `infra.style`:

| Style | What it is |
| --- | --- |
| `plain` | A hand-maintained CDK app. `package.json`, `tsconfig.json` and `cdk.json` are ordinary files the user owns and edits. **The default.** |
| `projen` | A projen project. `.projenrc.ts` declares an `awscdk.AwsCdkTypeScriptApp`, and projen derives the project files from it. |

**The stacks are the same either way.** `platform-stack.ts`, `service-stack.ts`,
`config.ts`, `app-config.ts` and `deploy-permissions.ts` are byte-identical across
styles, and so is the CloudFormation both produce. The choice is about who maintains
the scaffolding, not about what gets deployed.

That equivalence is the property to preserve. If a change makes one style synthesize
a different template than the other, the change is wrong.

"Byte-identical" is scoped to a fixed `pipeline.target`, not across targets:
`platform-stack.ts` conditionally instantiates the GitHub OIDC role via an optional
`githubActions` prop that `bin/app.ts`/`src/main.ts` populate only when the recorded
target is `github-actions`. The same manifest generated once for each target
therefore synthesizes platform stacks that differ by that role's presence — that
difference is expected and does not violate the equivalence this file is about.

## Asking

Ask it in Phase 2, batched with the pipeline target — both are generation-shape
questions and neither depends on analysis:

```
Infrastructure project style?

  plain    A normal CDK app. package.json, tsconfig.json and cdk.json are yours
           to edit. Nothing to learn. (default)

  projen   .projenrc.ts declares an AwsCdkTypeScriptApp and projen regenerates
           the project files from it. Pick this if the repo or the team already
           uses projen -- otherwise it is a tool to learn for no gain here.
```

Do not infer this from the repository. A projen file elsewhere in the repo is
evidence the user *knows* projen, not that they want the infra app managed by it.
Ask, and record the answer.

`projen` needs network access at generation time, for `npx projen@latest new`. Say so
when the user picks it in an environment where that may not hold.

## Layout

```
plain                             projen
-----                             ------
infra/                            infra/
  bin/app.ts                        .projenrc.ts        <- the project definition
  lib/config.ts                     src/main.ts         <- same content as bin/app.ts
  lib/app-config.ts                 src/config.ts
  lib/platform-stack.ts             src/app-config.ts
  lib/service-stack.ts              src/platform-stack.ts
  lib/deploy-permissions.ts         src/service-stack.ts
  scripts/ssm-preflight.sh          src/deploy-permissions.ts
  package.json                      scripts/ssm-preflight.sh
  tsconfig.json                     package.json    | generated by projen
  cdk.json                          tsconfig.json   | from .projenrc.ts --
                                    cdk.json        | never written by this skill
                                    .gitignore      |
                                    .projen/        |
```

`bin/app.ts` and `src/main.ts` differ **only** in their import paths: the plain entry
point reaches up into `lib/`, while the projen one imports its siblings, because
projen keeps every source under one directory. Both files are
carried in the skill, at [`../../assets/templates/cdk/bin/app.ts`](../../assets/templates/cdk/bin/app.ts)
and [`../../assets/templates/cdk-projen/src/main.ts`](../../assets/templates/cdk-projen/src/main.ts).
A change to either belongs in both, and this repository's `verify:styles` check
fails if they drift.

`scripts/ssm-preflight.sh` sits outside projen's world in both styles, so the
pipeline's path to it does not change.

## Generating the projen style

Order matters — `projen new` writes its own `.projenrc.ts`, so the template is
applied after it, not before:

1. **Bootstrap** in `infra/`:

   ```
   npx projen@latest new awscdk-app-ts \
     --name=<app>-infra --cdk-version=<cdkVersion> \
     --package-manager=npm --projenrc-ts --no-sample-code --no-git
   ```

   This exits non-zero, and that is expected: it runs eslint over an empty `src/`
   and TypeScript reports `TS18003: No inputs were found`. The project files are
   written regardless. Do not retry it, and do not add sample code to appease it —
   the next step turns eslint off.

2. **Overwrite `.projenrc.ts`** with
   [`../../assets/templates/cdk-projen/.projenrc.ts`](../../assets/templates/cdk-projen/.projenrc.ts),
   substituting `APP_NAME`, `CDK_VERSION`, and `DEFAULT_BRANCH`.

   `CDK_VERSION` is the `aws-cdk-lib` floor from
   [`../../assets/templates/cdk/package.json`](../../assets/templates/cdk/package.json)
   with the caret stripped — `^2.263.0` becomes `2.263.0`. Both styles pin the same
   floor on purpose, and it is the value recorded as `infra.cdkVersion`.

3. **Write the stack sources** into `src/`, and `scripts/ssm-preflight.sh` as usual.

4. **Run `npx projen`.** This installs dependencies, writes `package.json`,
   `tsconfig.json`, `cdk.json` and `.gitignore`, and produces `package-lock.json`.

5. **Delete the bootstrap leftovers.** `projen new` writes files that the options in
   step 2 then disable. Projen deletes their contents on the first synth — `LICENSE`,
   `.mergify.yml`, `.eslintrc.json`, and everything under `.github/` — but leaves the
   empty `infra/.github/` tree behind. Remove it. An empty `.github` under `infra/`
   reads like a workflow directory someone deleted the contents of.

   Leave the rest alone. `test/tsconfig.json`, `projenrc/tsconfig.json`,
   `.gitattributes`, `.npmignore` and `README.md` are projen's, not leftovers.

## Verifying

Both styles must synthesize **with no AWS credentials**. If credentials are needed,
something is doing an environment lookup, and that is a bug to fix rather than to
work around.

| Style | Command |
| --- | --- |
| `plain` | `npm ci && npx tsc --noEmit && npx cdk synth '**'` |
| `projen` | `npx projen && npx projen build` |

`npx projen build` compiles and then synthesizes both stacks, so it covers what the
two plain commands cover. The same false-positive validation warnings appear in both
— subnet IDs and role ARNs "not matching expected format", and an unreferenced
`vpc-id` parameter. They are described in the SKILL's completion section.

Both styles synthesize **the same CloudFormation, byte for byte**, from the same
manifest. If they ever don't, that is the bug — not something to reconcile in the
generated output.

## File ownership

The skill owns, and hash-tracks in `generated`:

- `plain` — every file under `infra/`.
- `projen` — `.projenrc.ts`, everything in `src/`, and `scripts/ssm-preflight.sh`.

Nothing else. The skill must **never** write or hash-track projen's outputs:
`package.json`, `tsconfig.json`, `cdk.json`, `.gitignore`, `.gitattributes`,
`.npmignore`, `.projen/`, `package-lock.json`, `test/tsconfig.json`,
`projenrc/tsconfig.json` — the full list is in `infra/.projen/files.json`, and it
grows with projen's versions, which is why ownership is an allowlist. Recording a
hash for one of them would make every `npx projen` run look like a user edit and
stall the next run on a diff nobody made.

To change any of them, change `.projenrc.ts` and re-run `npx projen`.

## On a re-run

`app-config.ts` is a plain source file in both styles, so the common case — a
finding changed, the config changed — needs no projen run at all.

Re-run `npx projen` only when `.projenrc.ts` itself is regenerated, which happens
when `app.name`, `pipeline.branch`, or the pinned CDK version changes.

A run whose recorded style differs from the style now requested is a **new project**,
not a conversion. Nothing converts an existing `infra/` in place: the new layout is
written and the overwrite check guards everything already on disk. Say that plainly
rather than half-converting a directory.

**Re-running against a manifest generated before the ECS service was given a
deterministic `serviceName`** replaces the `AWS::ECS::Service` on the next deploy —
`serviceName` is immutable, so CloudFormation cannot update it in place. Say so before
the deploy runs, not after. This is a one-time disruption per app, mitigated by the
service stack's rolling circuit breaker, not an ongoing concern.

## Pipeline implications

The deployment contract is unchanged: `npm ci`, then `npx cdk deploy <app>-service`.
Projen commits `package-lock.json` and puts `aws-cdk` in `devDependencies`, so both
steps work identically under either style. The pipeline never runs projen.

Two derived values do differ:

- **Path filter** — the service stack source is `infra/src/service-stack.ts` under
  projen, not `infra/lib/service-stack.ts`. Add `infra/.projenrc.ts` as well: it
  pins the CDK version the service stack is synthesized with.
- **The platform stack source** stays excluded, at whichever path it lives.
